# Навантажувальне тестування (завдання 2)

Сценарій: [`loadtest/notes.js`](../loadtest/notes.js) (k6). Запуск: [`loadtest/run.ps1`](../loadtest/run.ps1). k6 запускається в Docker-контейнері `grafana/k6:1.6.1`, тому окремо встановлювати його не треба.

## Команда запуску

```powershell
cd D:\univer\Cloud_Technologies\Lab1
.\loadtest\run.ps1 -Label baseline
```

Скрипт сам бере адресу сервісу з `terraform output app_url`, запускає k6 і зберігає звіт у `loadtest/results/<Label>.md` (і повні дані в `.json`).

Параметри (усі необов'язкові):

| Параметр | За замовчуванням | Що означає |
|---|---|---|
| `-Label` | `run` | назва прогону і файлу звіту |
| `-Vus` | `60` | N: кількість віртуальних користувачів на сталому навантаженні |
| `-RampUp` / `-Steady` / `-RampDown` | `3m` / `5m` / `2m` | тривалість трьох фаз |
| `-Think` | `0.3` | пауза між запитами одного користувача, с (випадкова в діапазоні 0.5–1.5 × Think) |
| `-Users` | `5` | скільки тестових акаунтів створити перед тестом |
| `-Mode` | `sync` | `async`: запис через чергу (`POST /notes/async`), бонус 6 |
| `-Local` | — | тест локального `docker compose` замість хмари |
| `-BaseUrl` | з `terraform output` | явна адреса |

Короткий пробний прогін для підбору N (≈2 хв):

```powershell
.\loadtest\run.ps1 -Label calibrate -Vus 60 -RampUp 30s -Steady 1m -RampDown 30s
```

## Профіль навантаження

**Мало записів, багато читань.** Перед тестом (`setup()` у k6) створюються 5 тестових акаунтів і отримуються їхні JWT-токени (параметр `-Users`, змінна `USERS`). Віртуальні користувачі по черзі беруть ці токени й у циклі роблять:

| # | Запит | Тип |
|---|---|---|
| 1 | `POST /notes` (з `Idempotency-Key`) | запис |
| 2 | `GET /notes?limit=20`: список постів | читання (кешується) |
| 3 | `GET /notes/{id}`: щойно створений пост | читання |
| 4 | `GET /users/{id}`: дані автора (власні) | читання |
| 5 | `GET /notes?limit=20` | читання (кешується) |
| 6 | `GET /notes/{id}`: випадковий пост зі списку | читання |
| 7 | `GET /notes?limit=20` | читання (кешується) |
| 8 | `GET /notes/{id}`: знову щойно створений | читання |
| 9 | `GET /users/{id}`: автор випадкового поста | читання |
| 10 | `GET /notes?limit=20` | читання (кешується) |

1 запис на 9 читань. Між запитами пауза ~0.3 с («думання» користувача).

**Три фази** (`ramping-vus`): наростання 0 → N за 3 хв, стале навантаження N 5 хв, спад N → 0 за 2 хв. Разом 10 хвилин, як вимагає умова.

**Як підібрано N.** Одна задача — 0.25 vCPU. Сталий CPU має бути помітно вищий за ціль 60 % (і за поріг алерту 70 %), щоб масштабування й лист гарантовано спрацювали. Пробний прогін `calibrate` (`-Vus 60`, 30 с / 1 хв / 30 с) дав 128 запитів/с, 0 % помилок, p95 40 мс і CPU однієї задачі ~85–90 %. Для основного прогону взято **N = 80**: одна задача з таким навантаженням не справляється (CPU ~100 %), тож масштабування мало гарантовано спрацювати і дійти більше ніж до 2 екземплярів.

**Чому акаунти створюються заздалегідь.** Пароль хешується PBKDF2 (200 000 ітерацій), і це навмисно повільно, щоб ускладнити перебір. У першому пробному прогоні кожен із 60 користувачів реєструвався й логінився на старті. Задача з 0.25 vCPU не встигала хешувати, і частина запитів `/auth/*` впала за таймаутом (2.18 % помилок, p95 запису ~30 с). Тобто тест міряв «шторм логінів», а не профіль «мало записів, багато читань». Тепер логіни відбуваються один раз до початку вимірювань, як у реальних навантажувальних тестах.

**Пороги k6** (тест «червоний», якщо порушено): помилок < 1 %, p95 читання < 1.5 с, p95 запису < 3 с.

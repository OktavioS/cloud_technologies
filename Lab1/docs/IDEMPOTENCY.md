# Ідемпотентність операцій запису (бонус 7)

## Як працює

`POST /notes` і `POST /notes/async` приймають заголовок **`Idempotency-Key`** (будь-який рядок 1–128 символів, зазвичай UUID). Код — [`app/idempotency.py`](../app/idempotency.py), використання — [`app/main.py`](../app/main.py).

```
POST /notes  Idempotency-Key: K  (тіло B)
   │
   ├─ Redis SET idem:user:<id>:K {"state":"processing","fp":hash(B)} NX EX 86400
   │     ├─ вдалося (ключ новий) ──► виконати INSERT ──► SET … {"state":"done","status":201,"body":…} EX 86400 ──► 201
   │     └─ ключ уже є:
   │           ├─ fp ≠ hash(B)          ──► 422 (ключ використано з іншим тілом)
   │           ├─ state = processing    ──► 409 (такий самий запит ще виконується)
   │           └─ state = done          ──► збережена відповідь, той самий статус + Idempotent-Replayed: true
   └─ INSERT упав ──► ключ видаляється, клієнт може повторити
```

- **Сховище:** спільний Redis, TTL **24 години** (`IDEMPOTENCY_TTL_SECONDS`).
- **Атомарність:** `SET ... NX` — це одна атомарна операція Redis. Навіть якщо два однакові запити одночасно потрапили на різні екземпляри, виконається лише один, а другий отримає `409`.
- **Простір ключів — на користувача** (`idem:user:<id>:<key>`): однакові ключі різних користувачів не конфліктують, і ніхто не отримає чужу відповідь.
- **Відбиток тіла (fingerprint):** SHA-256 від тіла запиту. Той самий ключ з іншим тілом — помилка клієнта (`422`), а не тихе повернення старої відповіді.
- Без заголовка запис працює як звичайно (кожен запит створює новий пост).

## Яку проблему це розв'язує

Мережа ненадійна. Клієнт надіслав `POST`, сервер створив пост, а відповідь загубилася (обрив з'єднання, таймаут балансувальника, мобільний інтернет). Клієнт не знає, чи запит виконався, і повторює його. Без ідемпотентності буде **два однакові пости**, а для платежу — дві оплати.

`POST` за визначенням HTTP **не ідемпотентний** (на відміну від `GET`, `PUT`, `DELETE`). `Idempotency-Key` робить його таким: клієнт генерує ключ один раз на «намір» і надсилає його в усіх повторах. Сервер гарантує, що намір виконається рівно один раз, а кожен повтор отримає ту саму відповідь. Так працюють Stripe, PayPal та інші платіжні API (є й чернетка стандарту IETF `Idempotency-Key`).

Сценарій навантаження теж надсилає `Idempotency-Key` з кожним записом (`loadtest/notes.js`).

## Як поєднується з чергою (бонус 6)

Ідемпотентність потрібна на **двох рівнях**, і обидва реалізовані:

1. **Клієнт → API.** Повтор `POST /notes/async` з тим самим ключем повертає **той самий `job_id`**, і в чергу не потрапляє друге повідомлення. Захищає від повторів клієнта.
2. **Черга → воркер.** SQS доставляє «щонайменше один раз», тож те саме повідомлення може прийти воркеру двічі. `job_id` пишеться в `notes.request_id UNIQUE`, а вставка `ON CONFLICT DO NOTHING` гарантує один запис ([QUEUE.md](QUEUE.md)). Захищає від повторів інфраструктури.

Разом це дає наскрізну гарантію «рівно один ефект» (effectively-once) поверх at-least-once доставки: від натискання кнопки до рядка в базі кожна операція виконується один раз, скільки б разів її не повторювали по дорозі.
